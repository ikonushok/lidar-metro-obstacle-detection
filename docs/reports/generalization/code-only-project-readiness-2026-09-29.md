# Анализ кода и гибкости

Дата: 2026-09-29. Режим code-only; проект lidar-metro-obstacle-detection; категория generalization; L0. Цель: отделить расширяемость программы от переносимости алгоритма.

## Карта реализации
PointCloud2/XYZ → AutoRails → наблюдаемая ось + tangent → CORE → Euclidean-компоненты → boundary / strong geometry / forest assist / early shape → temporal → JSON. Общее C++ ядро вызывают direct stream CLI и ROS2 node. Python обеспечивает чтение/каталог/evaluation; browser — просмотр. Обучаемая часть — 17 деревьев, восемь табличных признаков.

## Что гибко
- Ядро отделено от транспорта; оба адаптера используют общий алгоритм.
- Topic, ожидаемый frame, часть параметров поиска рельсов, профиль, margin и радиус кластеризации доступны в ROS2 параметрах (curve_envelope_node.cpp:31–63).
- Локальная ось извлекается из точек, поэтому нет зависимости от заранее построенной карты конкретного тоннеля.
- Raw CORE, отфильтрованные точки и диагностические статусы доступны отдельно. UNKNOWN не выдаёт разрешение движения.

## Что ограничивает перенос
1. **Высокий риск: hardcoded boundary.** curve_envelope_core.cpp:241–246, 863–864, 904–960: при >=250 точках левое тонкое высокое образование либо широкая объёмная компонента с centroid_z>1 объявляется warning. Это проверка абсолютных source XYZ, не расстояния до локального края габарита. Она выполняется до strong geometry и исключает компоненту также из early/assist.
2. **Высокий риск: размер/дальность forest.** baseline_v3_assist_model.inc:5–96: дерево 0 положительно только при объёме примерно 0.24–0.99 м³ и дальности 55.02–56.64 м; другие деревья используют ширину ~0.62–0.65 м и диапазоны высоты. Одно дерево не определяет лес, а лес не определяет весь pipeline. Но это явная зависимость части решения от признаков известной сцены.
3. **Средне-высокий риск: плотность.** Порог strong geometry равен 1000 точкам, connectivity radius 0.25 м фиксирован для всего диапазона. Разреженность может перевести объект в слабую ветку либо раздробить его; высокая плотность может повысить число фоновых тревог. Диапазонная нормализация в этом пути отсутствует.
4. **Средне-высокий риск: shape fallback.** curve_envelope_core.cpp:249–262: early требует >=80 точек, расстояние (7,80] м, depth<=0.8 м, abs(center_x)<=1.4; размеры куба 0.2–0.65 м либо панели 1.1–2.6 м по ширине/высоте. Непрерывного покрытия форм нет; near<=7 м исключён именно из early, не из всего детектора.
5. **Средне-высокий риск: установка/кривые.** auto_rails_core.cpp:154 задаёт s=-Y. AutoRailsConfig ограничивает боковой поиск, ширину пары 1.4–1.8 м и качество цепочки. Переименование frame не повернёт точки. Tangent экстраполирует последнюю касательную; на повороте возможны FP/FN.
6. **Средний риск: temporal без association.** CLI:363–385; ROS2:176–258, 471–475. Последовательность общих булевых сигналов подтверждает alarm через 2/3 кадра без доказательства, что это один объект. Early может дать FP от разных объектов; краткая видимость даёт пропуск. Задержка зависит от частоты и drops.

## Bug discovery и готовность
Кандидаты геометрического подавления и temporal association перечислены в отдельном bug-audit. Runtime-баги не воспроизводились. Архитектурная гибкость средняя; автоматическая адаптация к новому сенсору/монтажу низкая. Расширение возможно, но часть порогов требует изменения/пересборки C++, а не только JSON. JSON модели не полностью описывает current early-ветку: источником поведения остаётся код.

Evidence: перечисленные C++ файлы, hpp AutoRailsConfig/AnalysisResult, models/baseline_v3_runtime_policy.json, scripts/evaluate_baseline_v3_metrics.py. Команды: Get-Content и rg -n; git status/rev-parse, результаты в index.md. Компиляция и тесты не выполнялись. Не проверены фактические rail failures, latency и FN/FP. Остаточный риск высокий для новых физических условий. Следующий минимальный тест: фиксированный detector на новом positive-проезде, затем отдельная проверка плотности/поворота без перенастройки.
