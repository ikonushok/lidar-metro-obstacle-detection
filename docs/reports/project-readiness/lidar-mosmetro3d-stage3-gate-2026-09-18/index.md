Дата: 2026-09-18. Цель: определить, можно ли начинать этап 3 из `docs/work_plan.md`.

## Решение

- Вердикт: `PASS_WITH_RISKS` для **начала инженерной работы этапа 3**; `HOLD` для заявления о завершённом baseline.
- Практическая зрелость: технический прототип входа и визуального просмотра, а не MVP-детектор.
- Уровень валидации: L1 для двух входных replay и полного визуального рендера одного bag; L0 для геометрического решения и метрик детекции.
- Основание: этап 2 локализовал отсутствующий внешний контракт, а этап 3 добавил ограниченный `ASSUMED_HACKATHON` профиль для `lidar_livox`. Он разрешает лишь маркированный candidate и приближённую дистанцию; не даёт права на `CLEAR`, `NO_OBSTACLE`, safety-утверждения или измеримые TP/FP/FN.

Этап 3 следует начинать как минимальный контейнерный ROS2-конвейер с quality gate, загрузкой YAML, явными diagnostics и fail-safe состоянием `UNKNOWN`. Реальный envelope-only baseline с кластеризацией и расстоянием нельзя считать выполненным, пока не подтверждены frame/единицы, `working <- source`, профиль, путь и safety margin.

## Три главных риска

| Риск | Почему важен | Первое доказательство для снятия |
|---|---|---|
| Геометрия является demo-допущением | `ASSUMED_HACKATHON` активен только для candidate на `lidar_livox`; `CLEAR` и safety-decision запрещены | Документированный и проверенный `working <- lidar`, единицы, оси, профиль, путь и margin |
| Нет реализованного ROS2-детектора | В дереве есть только input audit/replay и визуальный stage 2; publisher результата, launch и кластеризация отсутствуют | Сквозной replay: PointCloud2 -> diagnostics/result -> визуализация/запись |
| Текущая тестовая команда не зелёная | При запуске текущих исходников в Humble image 12/13 тестов прошли; точное сравнение float в `test_gates_follow_reference_cross_section` упало | Исправленный тест и повторная проверка образа |

## Рекомендуемый порядок

1. Исправить воспроизводимо падающий unit-тест и повторить test suite.
2. До production заменить demo-допущения первичными источниками для frame, единиц, extrinsics, профиля, пути и margin; не объявлять нынешний YAML `VERIFIED`.
3. Создать task spec этапа 3 и реализовать guarded ROS2 baseline: при текущем контракте только `UNKNOWN` с причиной.
4. После подтверждения геометрии включить envelope, ROI, кластеризацию и расстояние; проверить границы, низкое препятствие и невалидный контракт.
5. Только затем проводить replay baseline и первые измерения. Разметка события и отдельный positive run по-прежнему нужны для метрик, а не для самого каркаса.
