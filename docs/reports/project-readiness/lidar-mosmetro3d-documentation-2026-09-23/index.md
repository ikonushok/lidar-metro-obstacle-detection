**Вывод: код значительно опережает общий план, а документация согласована с ним лишь частично.** Есть исследовательский прототип с C++ геометрией, ROS2-узлом, CPU viewer, моделью шума и синтетическими препятствиями. ## Самые важные расхождения

1. **Смысл обнаружения.** В плане шаг 3 выполнен как «каждый CORE return — candidate независимо от размера». Текущий ROS node принимает решение по `reportable_core_count`, а default CPU viewer использует `model_v1`; дерево оставляет только компоненты с высотой >0,366503 м и >104 точками. Raw CORE сохраняется, но сигнал может отсутствовать. Это нужно документировать и проверить на низких/малых объектах, а не молча возвращать старое поведение.
2. **Два разных пути.** Default viewer: archive → XYZ → direct C++ stream + model_v1 → HTTP → browser. ROS node: PointCloud2 → C++ + legacy filter. Совпадение геометрического ядра не означает совпадение конечного решения и задержки.
3. **Timing.** В текущем stream CLI общий timer уже включает оба фильтра; к нему повторно прибавляется один filter time. Lean-ветка достигается после обоих фильтров и wireframe. Документированная граница production-like измерения не выполняется.
