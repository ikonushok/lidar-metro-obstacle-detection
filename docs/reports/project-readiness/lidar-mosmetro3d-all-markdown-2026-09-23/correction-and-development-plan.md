## Идеи с проверяемой пользой

1. **Одна группировка CORE на кадр:** переиспользовать компоненты для признаков/решений; убрать второе вычисление legacy из обычного режима. Проверка — неизменные индексы/решения и меньший wall p95. Индекс соседей рассматривать после профиля O(n²)-поиска.
2. **Явная идентичность результата:** записывать commit/dirty hash, image id, effective config, model hash, dataset/frame/header, смысл таймеров. Это защищает документацию от смешения старых чисел, даже когда теги Docker прежние.
3. **Диагностика причин отказа:** отличать отсутствие точек/рельсовой опоры, участок synthetic continuation, raw CORE без reportable и отказ процесса. Не вводить новый safety-смысл без согласования схемы.
4. **Проверяемое переобучение:** JSON дерева и встроенный C++ должны иметь автоматическое сравнение на пограничных признаках и реальных компонентах. Простое сохранение нового JSON runtime не обновляет.

GPU, новый классификатор, карту, deskew и tracking не выбирать только из-за медленного открытия кадра. Включать конкретное расширение после того, как измерение показало соответствующую причину и есть необходимые входы.

Уровень этого плана — L0; manifest/11 tests — L1 согласно индексу. Не проверены новый benchmark, целевой стенд, независимое качество и математическая корректность всех исторических формул. Остаточный риск — оптимизировать не ту стадию или переобучиться на единственный положительный проезд. Следующая минимальная работа: D0–D2, затем R1; никакой незаявленной смены модели/геометрии план сам по себе не разрешает.
