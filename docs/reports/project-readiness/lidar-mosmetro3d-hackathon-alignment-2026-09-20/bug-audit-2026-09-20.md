## Конкретные следующие проверки

1. **Validation lifecycle.** Имеющийся HTTP-тест запускать только при явно поднятом каталоге; проверить default unit suite в новом контейнере без datasets/сервера. Предлагаемые файлы отдельной задачи: `tests/test_dataset_catalog_http.py`, `scripts/validate_stage_3.ps1`. Сначала выбрать контракт unit vs integration и test lifecycle; не скрывать failures общим skip без отдельной интеграционной команды. Полная новая сборка в этом аудите не выполнялась.
2. **CLI profile selection.** Минимальная проверка должна передать нестандартный config и наблюдать выбранный путь в создаваемом BaselineNode, отдельно для `--print-contract`, обычного CLI и ROS parameter. Предлагаемый новый файл: `tests/test_stage_3_cli.py`; возможная правка после проверки: `src/stage_3_baseline.py`. В этом аудите файл не создавался. Сигнал дефекта: обычный CLI продолжает выбирать default, когда ожидается переданный путь.
3. **UI lifecycle.** Использовать существующий `tests/test_auto_rails.cjs`; подтвердить ожидаемое отображение статуса пользователя и сохранить проверки очистки старой геометрии. Возможные файлы отдельной задачи — этот тест и/или `web/stage_2_review_layers.js`. Нельзя считать правильным просто ослабить весь lifecycle test.
