# Габарит поездов и универсальный контур

## Действующий C++ габарит

Статус: актуальные параметры `development_candidate / tangent`, 2026-09-23. [Запуск](../README.md), [методология](README_methodology.md). Профиль, единицы и монтаж остаются assumed; калибровка документацией не изменяется.

В локальном сечении оси пути CORE: x=[−1,4;1,4], z=[0;3,7] м; expanded: x=[−1,9;1,9], z=[−0,5;4,2] м. Прямоугольники протягиваются вдоль наблюдаемой оси и synthetic tangent-продолжения до `rail_forward_max_m` (80 м в текущем запуске). Источник — константы `src/cpp/curve_pipeline_stream_cli.cpp` и параметры общего ядра C++ ROS node. Старый YAML ниже не управляет этими константами.

Raw CORE сохраняется отдельно от reportable после model_v1. `system_status=UNKNOWN` и `safety_decision_permitted=false`; отсутствие сигнала не CLEAR. Расстояние измеряется от source origin, не от кузова/носа состава.

## Проектный универсальный контур и исторический Python baseline

Объединённый динамический габарит всего парка — проектная цель, а не реализованное и откалиброванное свойство текущего прямоугольного reference-профиля. Когда геометрия будет подтверждена, он будет использовать `universal_fleet_envelope` — объединение динамических габаритов всех поддерживаемых типов вагонов.

Такой контур консервативен: препятствие, опасное для любого поддерживаемого поезда, попадёт в него. Цена этого — возможные лишние тревоги для более узкого или низкого состава. Позже можно перейти на профиль конкретного поезда, если это даст измеримое уменьшение ложных тревог и будет подтверждено отдельной проверкой. Это не меняет общий интерфейс, входные данные или принцип работы системы.

Исторический Python Stage 3 baseline использовал явно маркированный профиль `ASSUMED_HACKATHON`: прямоугольник 2.800 × 3.700 м, straight path вдоль `-Y`, identity `hackathon_track_lidar_livox <- lidar_livox` и margin 0.20 условных метров. За ним расположен warning-layer: 0.50 м слева/справа/сверху и 1.30 м снизу. Core разрешает только `OBSTACLE_CANDIDATE_ASSUMED_GEOMETRY`, warning-layer — `WARNING_CANDIDATE_ASSUMED_GEOMETRY`, а отсутствие кандидата остаётся `UNKNOWN`; `CLEAR/NO_OBSTACLE` запрещены.

Перед production этот профиль подлежит полной замене: нужны первичный документ об осях/единицах, калибровка `target <- lidar`, динамический габарит, путь и safety margin. `ASSUMED_HACKATHON` не становится `VERIFIED` переименованием статуса или успешным demo-run.

## Калибровочные параметры и прежний YAML

| Что есть | Калибровочный параметр, которого не хватает | Поле в YAML | Комментарий |
|---|---|---|---|
| Справочный внешний контур 2.8 × 3.7 м | Утверждённый динамический габарит: форма кузова, нижнее оборудование, кривые, колебания | `universal_fleet_envelope.body_outline`, `underframe_outline`, `curve_sweep`, `dynamic_displacements` | Справочный прямоугольник не заменяет эти данные. |
| Полностью просмотренный bag и raw `frame_id` | Extrinsics `rail/train <- lidar`, подтверждённые оси и единицы | `frames.lidar_mounting_extrinsics`, `frames.axis_directions`, `frames.units` | Направление преобразования фиксировано как `target <- lidar`; его численные значения пока пусты. |
| Универсальная стратегия контура | Положение рельсов, путь и положение лидара относительно них | `path.rail_centerline_in_working_frame`, `path.lidar_pose_along_path` | Без пути нельзя перевести контур оси рельса в рабочий frame. |
| Историческое Python demo-допущение: margin 0.20 и inclusive intersection | Утверждённые safety margin и правило intrusion | `safety_envelope.margin`, `margin_unit`, `intrusion_rule` | Demo-параметр даёт только candidate, не safety-решение; production-значения нельзя выбирать по интуиции. |
| Протокол будущей оценки | Разметка реальных событий и расстояний | `evaluation_ground_truth.event_annotations_path`, `distance_reference` | Принятые 13–64 дают development frame-оценку; независимая событийная разметка/дистанция для итоговых метрик остаются необходимыми. |

В [`config/geometry_contract.yaml`](../config/geometry_contract.yaml) поля demo-профиля заполнены со статусом `ASSUMED_HACKATHON`, источником проектного допущения и запретом safety/clear решения. При получении внешних данных их нужно заменить в отдельной проверенной ревизии `VERIFIED`; не переносить demo-значения в production.

## Что должно войти в утверждённый контур

Недостаточно взять максимальные ширину и высоту из таблицы. Утверждённый универсальный контур должен включать форму кузова, нижнее оборудование, положение относительно рельсов, отклонения в кривых и допускаемые динамические перемещения. Для него также нужны подтверждённые оси, единицы, extrinsics лидара, путь и safety margin.

Справочный прямоугольник в YAML задан в условной системе `RAIL_CENTERLINE_REFERENCE`: горизонтально от -1.400 до +1.400 м относительно оси пути, вертикально от 0 до 3.700 м относительно уровня головки рельса. Это **не** система координат лидара и не разрешение использовать габарит для `CLEAR` или оценки расстояния.

Поля и статус такого контура хранятся в [`config/geometry_contract.yaml`](../config/geometry_contract.yaml). Правило его активации описано в [отчёте этапа 2](stages/stage_2/stage_2_geometry_config.md).
