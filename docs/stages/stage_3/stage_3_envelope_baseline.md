## Спецификация

- Goal: реализовать контейнерный ROS2 baseline для `lidar_livox`: PointCloud2 -> quality gate -> assumed-envelope candidates -> JSON result/diagnostics, затем визуально связать сохранённые core/warning clusters с кадрами плеера.
- Наблюдаемая проблема: после согласования demo-геометрии отсутствует исполнимый detector path и ROS2 output.
- Non-goals: `CLEAR/NO_OBSTACLE`, safety decision, поддержка `hesai_lidar`, TF, deskew, map subtraction, tracking, TTC, метрики качества и численные claims.
- Source of truth: ТЗ §3.3; `docs/work_plan.md` этап 3; `docs/methodology.md` §§6, 11, 15; `docs/dataset_audit.md`; `config/geometry_contract.yaml`.
- Этап: 3.
- Вход: `sensor_msgs/msg/PointCloud2`, active demo scope — `lidar_livox`; preserved source header/frame. Другой frame -> `UNKNOWN`.
- Рабочий frame и transform: `hackathon_track_lidar_livox <- lidar_livox`, identity и все метры имеют статус `ASSUMED_HACKATHON`.
- Режим: candidate-only envelope-only без background, deskew и temporal filtering. Нет candidate -> `UNKNOWN`; candidate -> `OBSTACLE_CANDIDATE_ASSUMED_GEOMETRY`; distance имеет метку `APPROXIMATE_M_ASSUMED_GEOMETRY`.
- Detection assumptions: ROI 0–200 m по `-Y`; core cross-section 2.8 × 3.7 m, expanded by margin 0.20 m; separate warning-layer outside profile: 0.50 m left/right/top and 1.30 m bottom; auto floor/rail profile может добавить candidate envelope, но прямой envelope остаётся fallback; numerical boundary tolerance 1e-6 m только для консервативного float comparison; voxel connected components, voxel 0.25 m, минимум 5 исходных точек. Все параметры — `ASSUMED_HACKATHON`, не acceptance thresholds.
- Allowed files: `.dockerignore`, `config/geometry_contract.yaml`, `src/stage_3_baseline.py`, `src/stage_3_metrics.py`, `src/stage_3_candidate_audit.py`, `scripts/run_stage_3_baseline.py`, `scripts/replay_stage_3_baseline.py`, `scripts/measure_stage_3_window.py`, `scripts/audit_stage_3_candidates.py`, `scripts/prepare_stage_2_player.py`, `scripts/run_stage_2_player.ps1`, `src/stage_2_player.py`, `web/stage_2_player.html`, `tests/`, `README.md`, `docs/stages/stage_2/`, `docs/stages/stage_3/`.
- Files to avoid: bag/TAR, ROS message schemas/QoS, TF contract, production profile and карта.
- Защищённые контракты: target <- source; raw timestamp/frame сохраняются; `UNKNOWN` не становится `CLEAR`; ни одна точка внутри assumed envelope не удаляется как rail/ground; результат не является safety decision.
- Safety reviewer: требуется из-за envelope, margin, clustering threshold и decision state.
- Validation reviewer: после safety-review; L1 target для unit/integration smoke, L0 для физических свойств допущений.
- Validation method: unit cases for candidate/no-candidate/invalid frame/invalid config/boundary; Docker build; unit suite; replay smoke if extracted bag is available.
- Acceptance criteria: Docker image builds; new tests pass; ROS2 node has configurable topics and output JSON/diagnostics; candidate/no-candidate modes satisfy the protected contracts; плеер отображает только сохранённые core/warning bounds и статус, без переинтерпретации их как safety decision.
- Stop conditions: не включать `CLEAR`, `geometric_decision_enabled` или safety decision; не заявлять detection quality or real-time; не активировать `hesai_lidar`.

Скрипт fail-closed проверяет точное совпадение result/manifest по количеству, header timestamp и source frame, затем вычисляет candidate rate только по bag offsets и p50/p95 только по `processing_ms`. В обоих окнах результат всегда core candidate; поэтому текущая конфигурация не различает `REF-002` и предварительное событие по самому факту candidate. Разница нормированных rate не интерпретируется как эффект события: интервалы короткие и имеют разный bag-time шаг. Покадровые summaries: `artefacts/stage_3/metrics/clean_visual_candidate_100_140.json` и `artefacts/stage_3/metrics/obs_003_150_170.json`.
- Read-only candidate audit: добавлены `src/stage_3_candidate_audit.py` и `scripts/audit_stage_3_candidates.py`. Для `REF-002` они построили 71 source-coordinate bins с размером 0.5 м; 16 присутствуют не менее чем в 33 из 41 кадров (80%). `artefacts/stage_2/player/candidate_audit.json` подхватывается плеером через переключатель `Audit: повторяемые ячейки*` и рисуется фиолетовым. Группы используют только bounds записанных candidate clusters: это recurrence невыравненных координат source frame, не tracking, static map, object identity или доказательство неподвижной инфраструктуры.

- Safety-review текущим агентом: `PASS_WITH_RISKS` для core/warning demo baseline. Проверено: `target <- source` и scope `lidar_livox` явны; unsupported `hesai_lidar` -> `UNKNOWN`; no candidate -> `UNKNOWN`; cluster только во внешнем слое -> `WARNING_CANDIDATE_ASSUMED_GEOMETRY`; `CLEAR`, safety decision, ground/rail removal, map, deskew и temporal confirmation отключены; boundary tolerance расширяет inclusion только на 1e-6 m и не уменьшает margin; low obstacle на z=0 остаётся core candidate. Это последовательный проход текущего агента, не независимое внешнее review.
- Safety-review текущим агентом для оверлея: `PASS_WITH_RISKS`. Оверлей читает только persisted bounds и отклоняет safety/clear result; он не меняет envelope, cluster, output node или решение. Это последовательный проход текущего агента, не независимое внешнее review.
- Safety-review текущим агентом для audit: `PASS_WITH_RISKS`. Audit читает persisted candidate bounds, не меняет конфиг/ROI/margin, не публикует ROS output и прямо маркирует отсутствие temporal alignment. Его фиолетовые boxes не являются картой, разрешённым exclusion или safety result. Это последовательный проход текущего агента, не независимое внешнее review.
- Validation-review текущим агентом: `PASS_WITH_RISKS`, L3 для одного изолированного end-to-end replay реального bag с точной проверкой 201 input/201 persisted results и ручным просмотром связанного плеера; L1 для unit contracts и воспроизводимого window metrics; L0 для физических свойств assumed geometry, event labels, detection quality и generalisation.
- Deliverables: Docker/Humble build — implemented; PointCloud2 quality gate — implemented; ROS2 candidate output/diagnostics — implemented; result recording — implemented; demo baseline for `lidar_livox` — implemented; `CLEAR`/production safety decision — not implemented by design; `hesai_lidar` demo profile — not implemented; metrics/FP/FN/latency quality — not claimed.
- Что не проверено: соответствие геометрии реальности; event boundaries/labels; подтверждённый clean negative run; другие пять bag; latency p95/queue/dropped frames; load/long-run; output consumer outside replay harness. `roundT_doubleT` имеет `hesai_lidar` и не является допустимым тестом active `lidar_livox` demo contract.
- Известные FP/FN или safety-риски: 201/201 candidate на одном bag без разметки доказывает доставку и работу алгоритма, но не TP и не FP. Наличие близких candidate points может отражать штатную инфраструктуру или ошибку demo-геометрии. Не использовать результат для утверждения о препятствии, свободном пути, дальности, recall, FP rate или real-time.
- Следующий минимальный тест: просмотреть и разметить один clean negative interval, затем измерить candidate rate/мин и p95 processing с неизменной config; только после этого проверять подавление штатной геометрии против зафиксированного baseline.
- Residual risk: contract and thresholds являются `ASSUMED_HACKATHON`; production требует отдельной `VERIFIED` ревизии и повторных boundary/replay tests.
