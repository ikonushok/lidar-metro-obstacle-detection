# Stage 5: baseline_v3 offline candidate validation

## Задача

- Goal: довести проверку `baseline_v3` как единого offline-кандидата.
- Наблюдаемая проблема или исходный claim: `baseline_v3` должен сохранять `doubleT_obstacle`, проходить `cloud_with_fake_obj` с TP=6, FN=0, FP=0 по оцениваемым событиям и не ухудшать старые отрицательные источники относительно сохранённых temporal summaries.
- Non-goals: не менять ROS2/C++ runtime, не делать push, не делать commit, не заявлять production/safety readiness.
- Source of truth: `docs/stages/stage_5/cloud_with_fake_obj_working_labels.json`, `scripts/evaluate_working_obstacle_labels.py`, `scripts/build_unified_offline_candidate.py`, сохранённые stage-5 артефакты.
- Пункт/раздел ТЗ и обязательный результат: offline evidence для выбранного метода; runtime/Humble/Docker не проверяется этой задачей.
- Этап docs/README_work_plan.md: stage 5 offline candidate screening/validation.
- Целевое окружение: Ubuntu 22.04 + ROS 2 Humble + Docker; фактическая среда проверки: локальный Windows workspace, `.venv`.
- Входные данные и единицы: покадровые JSON-артефакты; frame index в последовательности источника.
- Конкретный bag/версия/интервал, топик и объём выборки: используются сохранённые offline-артефакты stage 5; replay bag не выполняется.
- Факты из docs/README_dataset_audit.md, подтверждения на текущем входе и непроверенные предположения: `cloud_with_fake_obj` включён как 8-й источник; собственный synthetic/no100 трактуется как training/screening, не held-out.
- Рабочие frames и направление transforms: transforms не пересчитываются; используются уже сохранённые offline decisions.
- Режим baseline/расширений; необходимые TF/движение/карта/габарит и поведение при их отсутствии: `baseline_v3` = geometry-first, `model_v1_temporal` только для слабых/неочевидных случаев; `UNKNOWN != CLEAR`.
- Временная база событий и способ измерения вычислительной задержки: событие оценивается по frame windows; latency не измеряется.
- Allowed files: `docs/README_noise_classifier_v3.md`, этот stage-5 отчёт, `artefacts/stage_5/unified_offline_candidate_20260925/*`.
- Files to avoid: ROS2/C++ runtime, launch/config, message schemas, dataset raw files.
- Защищённые контракты: `UNKNOWN != CLEAR`; отрицательные boundary-события #7/#8 не считать помехой; synthetic/no100 не называть независимым held-out.
- Deliverables и статус каждого: README v3, refreshed JSON summaries, краткий validation вывод.
- Путь отчёта этапа или категории: `docs/stages/stage_5/stage_5_baseline_v3_offline_candidate.md`.
- Основной агент: `agents/lidar_obstacle_pipeline.md`.
- Нужен ли `safety_geometry_reviewer` и почему: отдельный safety-review не требуется, так как геометрия/runtime не меняются; проверяется сохранённая offline ветка.
- Нужен ли отдельный этап `validation_reviewer`; порядок и кто выполняет проходы: нужен validation-проход текущего агента по командам и JSON-результатам.
- Validation target: L1 для воспроизведения offline summaries, L4-ограниченно для multisource summary из сохранённых артефактов; не runtime L4.
- Validation method: пересобрать unified candidate JSON, прогнать event evaluator для `cloud_with_fake_obj` и `doubleT_obstacle`, сверить no100 и 8-source rows, посчитать matching union старых отрицательных источников из сохранённых geometry-аудит компонентов.
- Acceptance criteria: `cloud_with_fake_obj` TP=6, FN=0, FP=0; `doubleT_obstacle` TP=1 event/FN=0 and 52 TP frames; README содержит числа, отдельные FP/UNKNOWN колонки, русские пояснения.
- Stop conditions: если входные JSON отсутствуют, evaluator даёт отличающиеся результаты, или появляются изменения ROS2/C++ runtime.
