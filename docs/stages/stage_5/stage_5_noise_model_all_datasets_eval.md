## Спецификация

- Режим: validation; основной агент — текущий агент по `agents/lidar_obstacle_pipeline.md`, отдельный проход `agents/validation_reviewer.md`.
- Цель: одинаковым C++ входом сравнить текущий фильтр `CORE`-компонентов и сохранённое дерево на всех семи доступных записях до решения об интеграции в плеер.
- ТЗ: Ubuntu 22.04 / ROS 2 Humble / Docker; §8.3 оценивает задержку, частоту, ресурсы и стабильность без фиксированного числового порога. Наш p95 полного кадра, очередь и drops нужны для инженерной оценки; отдельный offline-прогон не доказывает runtime-качество.
- Входы: шесть bag из `dataset/for_hackathon/for_hackathon` и `new_data` из отдельного TAR. Source XYZ — конечные ненулевые точки, единицы `m_ASSUMED`; matching осуществляется в source frame без TF (`lidar_livox <- lidar_livox` либо `hesai_lidar <- hesai_lidar`).
- Label policy: единственный положительный интервал `doubleT_obstacle` 13–64 включительно; весь остальной поток считается отрицательным **по утверждению пользователя**, без независимой проверки объектов. На положительном кадре target — наибольший reportable компонент, подтверждённый `OBS-002` на кадре 55. Этот же проезд использован при обучении: метрики на нём development fit.
- Метрики: по кадрам TP/FP/FN/TN/UNKNOWN; компонентные ложные срабатывания; доля кадров с ложной тревогой; FP-кадры/мин и последовательные эпизоды/мин; C++ processing p95 и дополнительный Python postprocess p95 отдельно. Event recall по независимым препятствиям не оценивается.
- Allowed files: этот отчёт, `scripts/evaluate_noise_classifier.py`, сырые результаты в `artefacts/stage_5/noise_model_eval/`.
- Files to avoid: model artifact, C++/ROS2 production, геометрические конфиги, тестовая разметка, существующие незакоммиченные изменения.
- Контракты: `UNKNOWN` не становится `CLEAR`; raw CORE сохраняется, отрицательный прогноз только диагностический; модель не подключается к плееру.
- Целевой уровень: L4 для полноты offline-прогона семи существенно разных записей, но только L1 для классификационного качества по одному обучающему положительному событию и пользовательским отрицательным допущениям.
- Команда: `python3 scripts/evaluate_noise_classifier.py --root /workspace --output /workspace/artefacts/stage_5/noise_model_eval` в Docker `lidar-mosmetro3d:stage-4-cpu-viewer`; к каждому кадру применяется один и тот же C++ `curve_pipeline_stream_cli 2.0` и дерево v1.
- Acceptance: все 13 759 кадров обработаны без пропусков; компонентный split точно совпадает с индексами `reportable` текущего C++; сохранены поисточниковые JSON и сводка с именем и digest образа.
- Stop conditions: несовпадение split с C++, ошибочный source frame/схема, неполный источник либо расхождение счётчика кадров.

## Результат

- Claim / verdict: модель снижает число кадров тревоги по пользовательской разметке на семи доступных записях — `PASS_WITH_RISKS` для offline-сравнения. Claims об обобщении на новый объект, runtime-скорости или безопасности — `HOLD`.
- Фактическая команда: `docker run --rm --mount "type=bind,source=$((Get-Location).Path),target=/workspace" -w /workspace -e PYTHONPATH=/workspace/scripts:/workspace/src lidar-mosmetro3d:stage-4-cpu-viewer python3 scripts/evaluate_noise_classifier.py --root /workspace --output /workspace/artefacts/stage_5/noise_model_eval` — exit 0. Предварительный smoke на кадрах 74–83 `doubleT_obstacle` — exit 0, старый фильтр 7 FP-кадров, модель 0.
- Среда: Docker image `sha256:9bfb031b0f4cd728a9c25e85fc7b335f25b26894e3e9b77b4decea15bb9cb812`, Linux в WSL2, Python 3.10.12; модель SHA256 `8C3E0B83A240E4D61932E475B70A878FFDDA65927ABCCBA5A5861AA4ADC4A53E`. Локальный компьютер не равен целевому стенду ТЗ.
- Область: 13 759/13 759 ожидаемых кадров семи источников, ошибок десериализации/обработки нет. 193 кадра `UNKNOWN`, они не объявлены `CLEAR` и не входят в TN. Сверка Python-связности компонентов с C++ reportable source indices прошла на каждом поддержанном кадре.
- Метрика: frame-level alarm. В отрицательном кадре любое число reportable компонентов — один FP-кадр; в положительном кадре отдельно отслеживается target-компонент. Это не object/event precision. - Снижение FP-кадров по условной отрицательной разметке — 90,5%. На независимых от обучения отрицательных записях модель оставила 457 FP-кадров. Ни одного независимого положительного события для расчёта recall новых препятствий нет.
- Latency scope: `processing_ms` C++ уже включает старый фильтр, `postprocess_ms` измерено отдельно монотонными часами Python после получения JSON. Ни одно из этих чисел не является p95 полной цепочки с интегрированной моделью. Ориентир ~100 мс при ~10 Гц превышен C++ p95 на пяти записях; ТЗ §8.3 числового порога не задаёт. Скорость по ТЗ и устойчивость real-time — не доказаны.
- Validation level achieved: L4 только для полноты offline-прогона нескольких записей и проверки согласованности компонентов; L1 для классификационного качества на одном обучающем положительном событии. `new_data` полностью пройден, но отрицательная разметка не подтверждена независимым просмотром.
- Validation review текущим агентом: `PASS_WITH_RISKS` для количества обработанных кадров и сравнительных frame-level counts; `HOLD` для утверждения о качестве на новых объектах и для соответствия runtime-скорости ТЗ.
- Непроверенные пункты: новые препятствия, малые/низкие объекты, object/event matching, точность геометрии и профиля, C++ evaluator модели, ROS2 replay с очередью/drops, целевой стенд i7-9700E, скрытый контрольный bag.
- Остаточный риск: дерево выучило пороги `extent_z > 0,366503 м` и `point_count > 104`; новые объекты ниже/разреженнее будут подавлены при прямом использовании. Встраивание без независимого положительного теста может скрыть опасную помеху.
- Следующий минимальный тест: получить отдельный положительный проезд с малым и низким препятствием; сравнить дерево с небольшими Random Forest/LightGBM на тех же целых проездах, затем измерить финальный C++/ROS2 конвейер на стенде ТЗ до изменения решений плеера.
