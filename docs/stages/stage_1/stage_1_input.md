## Спецификация

- Режим: patch → validation; пользователь одобрил выполнение этапа 1.
- Goal: воспроизводимые сборка Humble, чтение и replay двух bag, статистика и визуализация входа.
- Источник истины: ТЗ §3–5; этап 1 `docs/work_plan.md`; docs/dataset_audit.md; docs/methodology.md §§4–5.
- Среда: Ubuntu 22.04 / ROS 2 Humble / Docker; хост Windows Docker Desktop.
- Данные: полные roundT_doubleT и doubleT_obstacle из исходного TAR. Единицы и геометрическая калибровка не подтверждены.
- Frames: исходные hesai_lidar/lidar_livox; transforms не применяются.
- Часы: bag/header/per-point раздельно; время обработки — perf_counter.
- Non-goals: детектор, envelope, калибровка, TF, фильтрация геометрии, карта, deskew, tracking, TTC.
- Allowed files: Dockerfile, .dockerignore, .gitignore, requirements.txt, .python-version, src/, scripts/, tests/, config/, docs/, artefacts/; извлечённые копии только в dataset/extracted/.
- Files to avoid: исходный TAR, существующие чужие изменения и корневой README (инструкция запуска отдельным документом).
- Защищённые контракты не меняются. Адаптация зависимостей к Humble и новый диагностический подписчик входят в одобренный план; QoS выбирается по записанному publisher QoS, факты фиксируются.
- Роль: текущий агент по lidar_obstacle_pipeline; отдельный проход validation_reviewer после реализации. Safety-review нужен только при изменении геометрии, которого здесь нет.
- Deliverables: контейнер; валидатор PointCloud2; offline audit; ROS subscriber/replay smoke; изображения; инструкция; отчёт.
- Target: L1 для входного этапа, без утверждений о качестве детекции.
- Test plan: unit-тесты endian/offset/count/row padding/повреждения/NaN; docker build; offline audit полных двух bag; replay со сверкой количества; повтор команды с альтернативным путём.
- Acceptance: обе записи декодируются, сообщения и ошибки подсчитаны, изображения просмотрены; сборка и запуск воспроизводимы.
- Stop: не подменять UNKNOWN статусом CLEAR; не назначать единицы/оси; невозможность runtime фиксировать блокером.

## Результаты

Выполнен входной этап 1. Docker Desktop восстановлен после сбоев двух служебных сокетов; подробности в `docs/reports/bug-reproducer/bug-reproducer-report.md`.

Первый replay обычного bag со стандартным транспортом получил 48/252 сообщений при успешном завершении player. Исходные результаты сохранены в `artefacts/stage_1/roundT_doubleT/replay-default-transport.json`. Проверка shared-memory 128 MiB получила 28/252; сама по себе не принята как исправление. Raw-подписка с явной десериализацией также получила 28/252; гипотеза, что достаточно сменить Python-путь приёма, не подтвердилась. Эти эксперименты не меняют QoS, схему сообщения или исходные данные.

Локальная копия bag в Linux дала 240/252; локальная копия с SHM 128 MiB — 247/252; ожидание DDS acknowledgements — 241/252. В последнем случае все 11 пропусков находились среди первых 14 кадров. Запуск из паузы с ожиданием обработки первого кадра, затем resume, дал 252/252 в двух последовательных запусках. Это доказательство работоспособного сценария запуска, не доказательство единственной внутренней причины потерь rosbag2/DDS. Полная причинная абляция всех сочетаний не выполнялась.

### Отдельная проверка геометрии и времени

Текущий агент проверил код отдельным проходом: исходные frames и timestamps сохраняются; преобразования и калибровка не вводятся. Нулевые/нечисловые точки исключены только из статистики координат и изображений с сохранением счётчиков, исходные сообщения не меняются. Решение о свободном габарите не выдаётся. Это не независимое внешнее review.

### Финальная validation — 2026-09-18

Отдельный проход текущего агента по `agents/validation_reviewer.md`: **PASS_WITH_RISKS, L1 для проверки входа**. Это не L3 всего детектора. Итоговый `scripts/validate_stage_1.ps1` завершился с кодом 0.

Среда: Intel Core Ultra 7 265K, 20 физических/логических ядер; Windows сообщает 68 043 718 656 байт RAM (около 63.4 GiB), Docker доступно 47.04 GiB. Ubuntu 22.04.5 / Python 3.10.12 / rclpy 3.3.21 / NumPy 1.21.5. GPU не используется. Пиковый RSS процесса-подписчика: обычная запись 232.66 MiB, obstacle 324.64 MiB; это не память всего контейнера и player. Срезы Docker stats сохранены отдельно; непрерывный peak CPU/RAM контейнера не измерялся. Проверенный во время аудита контейнер имел OOMKilled=false; отсутствие OOM всех прошлых процессов не доказано. Наблюдаемые потери не были свидетельством исчерпания 64 GB RAM.

Основные команды:

```powershell
python scripts/extract_stage_1.py
docker build --progress plain -t lidar-mosmetro3d:stage_1 .
./scripts/validate_stage_1.ps1
```

На Windows извлечение фактически выполнялось Python из bundled runtime Codex; скрипт использует стандартную библиотеку. Дополнительно выполнялись локальные unit-тесты (6/6), разбор AST пяти Python-файлов, git diff --check; успешные проверки. Docker запускался с повышенным доступом из-за ограничений sandbox. Проверки схемы/статистики сделаны на всех 453 облаках, а не на 12 облаках первичного аудита.

Артефакты: `artefacts/stage_1/build.log`, `build-final.log`, `tests.log`, `environment.log`, `host-*.json`, `container-stats.jsonl`, `sequence-check.json`; в подкаталогах bag — frames.jsonl, summary.json, replay.json, player.log и три PNG. Финальный image config digest: `sha256:e508015a44ff71d91c80bbc6af5ae8e0ddc9aaa80994c1d8a179e08e880cc077`.

Изменения: Dockerfile и настройка DDS; декодер `src/cloud_input.py`; скрипты извлечения/audit/replay/проверки; шесть unit-тестов; описание окружения; дополнение аудита и статуса плана. Исходный TAR и геометрические данные не изменялись. Ранее существовавшие изменения README/AGENTS и других файлов сохранены.

Ограничения: старт из паузы и первый шаг — явное условие проверенного replay, не имитация непрерывного датчика. Время callback не включает DDS-очередь и не является задержкой детектора. Оба bag использовались для разработки входа; независимый тест качества не заявляется. Не проверены остальные четыре bag, новые форматы, связи часов, калибровка, габарит, потеря TF, непрерывная эксплуатация и восстановление Docker после перезагрузки Windows. Полный визуальный просмотр obstacle и разметка остаются следующим этапом.
