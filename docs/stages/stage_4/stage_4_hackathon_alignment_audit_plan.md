Дата: 2026-09-20. Режим: inspect / docs-vs-code, этап 4 (оценка текущей готовности, не закрытие этапа).

- Цель: ответить, соответствует ли направление работы ТЗ, на каком этапе находится проект и что отвлекает от результата.
- Источник обязательств: полный текст `docs/hackathon_documentations/5. ДепТранспорта.pdf`. Evidence: текущие код/config/scripts/tests, сырые JSON результатов в artefacts; README и план — заявления, не доказательства. Старые readiness/bug-аудиты не используются.
- Scope: вход → геометрия/детектор → ROS2/плеер → оценка → воспроизводимая сдача. Отдельно короткий перенос на new_data и поддержанная дальность.
- Non-goals: менять production-код, пороги, геометрию, интерфейсы, datasets или воспроизводить новые баги изменением файлов. Не требовать сертификации/production готовности для хакатона.
- Allowed files: эта спецификация; новый пакет в `docs/reports/project-readiness/lidar-mosmetro3d-hackathon-alignment-2026-09-20/`; сырые материалы проверки в `artefacts/audit/hackathon_alignment_20260920/` при необходимости.
- Основная роль: текущий агент; project-readiness-auditor, отдельный validation-проход того же агента. PDF skill для чтения ТЗ. Без субагентов.
- Защищённые контракты: UNKNOWN != CLEAR; source frame и временные базы не меняются; все найденные противоречия только описываются. Новые reproduction tests и исправления вне scope.
- Проверки: извлечение требований из PDF; трассировка CLI/node/UI/evaluator; чтение первичных JSON; существующие узкие тесты при доступном окружении. Никаких новых длительных replay или rebuild без необходимости.
- Target: статический аудит плюс L1 только там, где есть конкретная выполненная узкая проверка; исторические артефакты не подтверждают автоматически текущую версию.
- Acceptance: таблица «ТЗ → evidence → пробел», практический этап, вывод о фокусе работ и минимальная следующая серия задач; отдельные code/readiness/bug reports с индексом, без неподтверждённых процентов готовности.
- Stop: отсутствие калибровки/разметки фиксировать как missing evidence, а не как доказанный провал алгоритма; не запускать изменение системы ради аудита.
- Остаточный риск: отдельные результаты и UI могут изменяться параллельно; фиксировать область и команды конкретной проверки. Следующий минимальный тест определит итоговый отчёт.
