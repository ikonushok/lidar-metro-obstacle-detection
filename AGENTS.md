# lidar_MosMetro3D — правила для агентов

Project: lidar_MosMetro3D

Этот файл задаёт правила для проекта обнаружения посторонних объектов в тоннеле метро по данным 3D-лидара и переопределяет инструкции родительского проекта о дорожных дефектах для всего этого поддерева.

Пользовательские ответы — на русском языке. Имена кода, ROS2-топиков, сообщений и параметров сохранять в стиле проекта.

## Экономия токенов и контекста

- По умолчанию работать экономно: читать только файлы, необходимые для текущей задачи.
- Не выполнять широкий аудит, поиск по всему проекту и чтение больших документов без явной причины.
- В ответах давать краткий вывод и только ключевые evidence/команды.
- Расширять контекст только когда это нужно для безопасности, архитектурного решения, проверки требований или явного запроса пользователя.

## Источники истины

Различать требования, выбранный метод и доказательства:

1. `docs/hackathon_documentations/5. ДепТранспорта.pdf` — обязательства конкурса и условия сдачи. Целевая среда: **Ubuntu 22.04 + ROS 2 Humble + Docker**. Несоответствие текущего кода ТЗ — задача адаптации, не основание переопределять ТЗ.
2. Фактические код, конфигурации, ROS2-интерфейсы, данные, тесты и вывод команд — доказательства текущего состояния, но не доказательство выполнения требований без проверки.
3. `docs/METHODOLOGY.md` — выбранный метод и границы режимов; `docs/DEVELOPMENT_HISTORY_AND_STATUS.md` — порядок работ, текущая очередь, границы этапов и статус будущих проверок.
4. `docs/DATASETS_AND_ASSUMPTIONS.md` — единый реестр наблюдений по входу, границ выборки и открытых вопросов. Различать сведения о всех шести базах, свойства 12 исследованных облаков и гипотезы; не распространять выборку на весь набор без проверки.
5. `docs/SUBMISSION_CHECKLIST.md` — практический чеклист упаковки и сдачи текущего репозитория; он не заменяет ТЗ и не доказывает runtime без команд.
6. `docs/reports/submission/` — evidence-отчёты по уже выполненным проверкам. Использовать их как датированные доказательства с указанным уровнем валидации, не переносить автоматически на изменённую версию.
7. README, заявки и презентации — описание/намерение, не runtime evidence. Предположения маркировать и снабжать планом проверки.

При конфликте явно указать требование ТЗ, фактическое состояние и необходимое изменение. Прежние локальные настройки под Jazzy не считать проверенной средой Humble; их миграцию выполнять отдельной задачей с проверкой сборки.

## Working Rules / Рабочий порядок

1. Начать с `agents/context_router.md` и загрузить только нужный контекст.
2. Для нетривиальной задачи создать экземпляр по `agents/task_spec_short.md` в каталоге её этапа: `artefacts/task_specs/<purpose>.md`; шаблон не перезаписывать.
3. Основную реализацию вести по `agents/lidar_obstacle_pipeline.md`.
4. Подключать `agents/safety_geometry_reviewer.md` только по его триггерам.
5. Перед утверждением о качестве, тестах или готовности использовать `agents/validation_reviewer.md`.
6. Разделять реализацию, safety-review и проверку доказательств.
7. Делать минимальное изменение, сохраняющее наблюдаемость промежуточных стадий.
8. Исторический первый результат — контейнерный envelope-only baseline; текущий путь дополнен model_v1 и двумя C++ адаптерами. Базовый контракт: проверенный вход, наличие препятствия, ближайшее расстояние и diagnostics. Карта, deskew, tracking и TTC включаются после проверки необходимых входов и эффекта, не блокируют первый baseline.
9. Сохранять текущие роли. На одном этапе использовать не более одного reviewer; при пересечении триггеров сначала отдельный safety-review изменения, затем validation результатов. Название роли не требует автоматического запуска субагента: допускаются отдельные явно обозначенные проходы текущего агента, без заявления о независимости такого review.

## Структура документации и отчётов

- Task spec, план и отчёт рабочей задачи хранить в ignored `artefacts/task_specs/<purpose>.md`; новые публичные docs добавлять только по явной необходимости.
- Для подготовки сдачи различать: `docs/DEVELOPMENT_HISTORY_AND_STATUS.md` — очередь и границы работ; `docs/SUBMISSION_CHECKLIST.md` — упаковочный чеклист; `docs/reports/submission/` — датированные evidence-отчёты.
- Прочие отчёты хранятся в `docs/reports/<category>/`. Отчёты bug-reproducer — в `docs/reports/bug-reproducer/`.
- Корневой каталог `reports/` для новых отчётов не использовать. Артефакты запусков, изображения и сырые журналы хранятся в `artefacts/`.
- В каждом новом отчёте указывать цель, относящийся этап или категорию, изученные evidence, выполненные команды и результаты, уровень валидации, непроверенные пункты, остаточный риск и следующий минимальный тест.

## Инварианты безопасности

- `DEGRADED/UNKNOWN` никогда не трактуется как `CLEAR/NO_OBSTACLE`.
- Направление каждого преобразования координат указывается явно: `target <- source`.
- Отсутствие `/tf` допустимо, если преобразование не требуется и габарит определён в проверенном рабочем frame. Отсутствие необходимого преобразования или неустановленный габарит означает `UNKNOWN`; переименование frame не заменяет калибровку.
- Deskew требует времени точек и валидной оценки движения в согласованной временной базе. Для накопления кадров также необходимо проверенное совмещение.
- Bag/header/per-point timestamps не смешиваются без установленной связи часов. Вычислительную задержку измерять монотонными часами процесса.
- Порог, margin, range band, окно подтверждения и вес риска — параметры калибровки, а не универсальные константы.
- Новая геометрия не добавляется автоматически в доверенный background.
- Точки внутри safety envelope нельзя удалять как «землю/рельсы» без отдельного доказательства и теста на низкие препятствия.
- Distance-aware обработка оценивается отдельно по диапазонам дальности.
- Временной фильтр не должен скрывать немедленное предупреждение о глубоком или близком intrusion.
- Геометрический confidence не называется вероятностью аварии без отдельной калибровки.
- Хакатонный MVP не описывается как production-ready или сертифицированная система.

## Forbidden Changes / Запрещённые неявные изменения

Не менять без явного согласования и тестового плана:

- системы координат, оси, единицы, временную базу и TF-контракты;
- профиль поезда, safety margin и геометрию envelope;
- правила построения или обновления static map;
- пороги background subtraction, clustering, temporal confirmation и risk level;
- схемы ROS2-сообщений, QoS и диагностические состояния;
- единицу разбиения development/calibration/test;
- смысл метрик, object/event matching и критерии acceptance;
- зависимости, ML-компоненты и прямой контур управления поездом.

## Минимальная отчётность после изменения

- что изменено и зачем;
- какие файлы и данные изучены;
- какие команды фактически выполнены и с каким результатом;
- достигнутый уровень доказательств;
- что осталось непроверенным;
- остаточные риски и следующий минимальный тест.

## Уровень валидации

Current validation level: L0 для изменённой версии до успешной проверки пакета; подтверждённый результат и дату хранить в отчёте задачи.

Уровень фиксировать в отчёте конкретной проверки, с командой и областью утверждения. Не переносить результат старой проверки на изменённую версию пакета автоматически.

Пак инструкций может достичь L2 после статической и межфайловой проверки. Это не доказывает работоспособность LiDAR-конвейера. Runtime, метрики и готовность к эксплуатации требуют отдельных доказательств.
